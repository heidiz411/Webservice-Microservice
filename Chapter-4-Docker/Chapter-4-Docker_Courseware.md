### 1.1 วัตถุประสงค์การเรียนรู้ (Learning Objectives — ตาม Bloom’s Revised Taxonomy)

เมื่อเรียนจบบทเรียนนี้ นักศึกษาจะสามารถ:

1.  **(Remember)** ระบุความหมายของคอนเทนเนอร์ อิมเมจ และรีจิสทรี รวมถึงคำสั่ง
    Docker พื้นฐานที่ใช้บ่อยได้

2.  **(Understand)** อธิบายความแตกต่างระหว่างคอนเทนเนอร์กับเครื่องเสมือน
    (Virtual Machine) และอธิบายกลไกการทำงานแบบชั้น (layer) ของอิมเมจได้

3.  **(Apply)** เขียน Dockerfile เพื่อบรรจุแอปพลิเคชันของตนเองเป็นอิมเมจ
    และรันเป็นคอนเทนเนอร์ที่เข้าถึงได้จริงได้

4.  **(Analyze)** วิเคราะห์สาเหตุที่คอนเทนเนอร์ทำงานผิดพลาด จากบันทึกการทำงาน
    (logs) สถานะคอนเทนเนอร์ และการตั้งค่าเครือข่าย/พื้นที่จัดเก็บได้

5.  **(Evaluate)** ประเมินคุณภาพและความปลอดภัยของ Dockerfile ตามแนวปฏิบัติที่ดี
    เช่น ขนาดอิมเมจ การใช้แคช และสิทธิ์ของผู้ใช้ในคอนเทนเนอร์ได้

6.  **(Create)** ออกแบบและสร้างระบบหลายบริการ (เว็บแอปพลิเคชัน + ฐานข้อมูล)
    ด้วยไฟล์ Compose ที่รันได้ด้วยคำสั่งเดียวได้

## ส่วนที่ 2: บทนำ — ปัญหา "ในเครื่องผมรันได้นี่ครับ"

สถานการณ์ที่นักศึกษาทุกคนเคยเจอ: โปรแกรมที่เขียนเสร็จและทดสอบผ่านบนเครื่องตนเอง
กลับรันไม่ได้เมื่อส่งให้เพื่อนหรือติดตั้งบนเซิร์ฟเวอร์ สาเหตุคือ **ความแตกต่างของสภาพแวดล้อม
(environment)** ได้แก่ เวอร์ชันของภาษาโปรแกรม ไลบรารีที่ติดตั้งไว้ ตัวแปรระบบ
ระบบปฏิบัติการ และการตั้งค่าต่าง ๆ ซึ่งไม่มีทางเหมือนกันทุกเครื่อง

**แนวคิดของ Docker** คือการแก้ปัญหานี้ที่ต้นเหตุ ด้วยการบรรจุ **โปรแกรม + ไลบรารี +
สภาพแวดล้อมทั้งหมด** ไว้ในหน่วยเดียวที่เรียกว่า **คอนเทนเนอร์ (Container)**
แล้วส่งมอบทั้งหน่วยนั้นไปทำงานที่ใดก็ได้ ผลลัพธ์คือสิ่งที่รันบนเครื่องนักศึกษา
จะเป็นสิ่งเดียวกันกับที่รันบนเซิร์ฟเวอร์จริงทุกประการ

Docker เผยแพร่ครั้งแรกเมื่อวันที่ 20 มีนาคม ค.ศ. 2013 โดย Solomon Hykes
เขียนด้วยภาษา Go
และปัจจุบันกลายเป็นทักษะพื้นฐานที่อุตสาหกรรมซอฟต์แวร์คาดหวังจากบัณฑิตสายไอที
เพราะเป็นรากฐานของงาน DevOps ระบบไมโครเซอร์วิส (Microservices)
และการทำงานบนคลาวด์

| **เปรียบเทียบให้เห็นภาพ:** การส่งของทางเรือเคยยุ่งยากเพราะสินค้าแต่ละชนิดมีรูปทรงต่างกัน จนกระทั่งมีการคิดค้น "ตู้คอนเทนเนอร์มาตรฐาน" ซึ่งทำให้เรือ รถบรรทุก และเครน ไม่ต้องสนใจว่าข้างในเป็นอะไร ขอเพียงขนาดตู้เป็นมาตรฐานเดียวกัน — Docker ทำสิ่งเดียวกันกับซอฟต์แวร์ |

## ส่วนที่ 3: แนวคิดพื้นฐานของคอนเทนเนอร์

### 3.1 คอนเทนเนอร์ต่างจากเครื่องเสมือนอย่างไร

ทั้งสองเทคโนโลยีสร้าง "สภาพแวดล้อมแยกส่วน" เหมือนกัน แต่แยกที่ระดับต่างกัน เครื่องเสมือน
(VM) จำลองทั้งเครื่องรวมถึงระบบปฏิบัติการของตนเอง ส่วนคอนเทนเนอร์
**ใช้เคอร์เนลของระบบปฏิบัติการโฮสต์ร่วมกัน** แล้วแยกเฉพาะส่วนที่จำเป็น ซึ่งเรียกเทคนิคนี้ว่า
OS-level virtualization

| **ประเด็น**    | **เครื่องเสมือน (VM)**                         | **คอนเทนเนอร์ (Container)**                       |
|---------------|---------------------------------------------|--------------------------------------------------|
| ระบบปฏิบัติการ   | มี OS เต็มรูปแบบของตนเองในแต่ละเครื่อง            | ใช้เคอร์เนลของโฮสต์ร่วมกัน                            |
| ขนาด          | หลาย GB                                     | ตั้งแต่ไม่กี่ MB ถึงหลายร้อย MB                          |
| เวลาเริ่มทำงาน  | หลายสิบวินาที ถึงนาที                            | ระดับวินาทีหรือน้อยกว่า                                |
| ระดับการแยกส่วน | แยกขาดในระดับฮาร์ดแวร์เสมือน จึงปลอดภัยกว่า        | แยกที่ระดับกระบวนการ (process) เบากว่าแต่แยกขาดน้อยกว่า |
| เหมาะกับงาน    | ต้องใช้ OS ต่างชนิด หรือต้องการความปลอดภัยระดับสูงสุด | ติดตั้งใช้งานแอปพลิเคชันจำนวนมาก ปรับขยายรวดเร็ว         |

| **ข้อควรระวังที่ต้องย้ำ:** เพราะคอนเทนเนอร์ใช้เคอร์เนลของโฮสต์ร่วมกัน คอนเทนเนอร์ Linux จึงรันบนเคอร์เนล Linux เท่านั้น การรัน Docker บน Windows หรือ macOS จึงต้องอาศัยเครื่องเสมือน Linux เบื้องหลัง (เช่น WSL2 บน Windows) ซึ่งเป็นเหตุผลว่าทำไมประสิทธิภาพบนสองระบบนี้จึงต่างจาก Linux โดยตรง |
|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

### 3.2 คำศัพท์หลัก 4 คำที่ต้องแยกให้ออก

- **Image (อิมเมจ) —** แม่แบบแบบอ่านอย่างเดียว ที่บรรจุระบบไฟล์ ไลบรารี
  และคำสั่งเริ่มทำงานของแอปพลิเคชัน เปรียบได้กับ "คลาส" ในการเขียนโปรแกรมเชิงวัตถุ
  หรือ "แผ่นติดตั้งโปรแกรม"

- **Container (คอนเทนเนอร์) —** อิมเมจที่ถูกนำมารันจริงเป็นกระบวนการทำงาน
  เปรียบได้กับ "อ็อบเจกต์" ที่สร้างจากคลาส หนึ่งอิมเมจสร้างได้หลายคอนเทนเนอร์พร้อมกัน

- **Registry (รีจิสทรี) —** คลังเก็บอิมเมจสำหรับแบ่งปัน ที่นิยมที่สุดคือ Docker Hub
  เปรียบได้กับ GitHub แต่เก็บอิมเมจแทนซอร์สโค้ด

- **Dockerfile —** ไฟล์ข้อความที่เขียนคำสั่งบอกวิธีสร้างอิมเมจทีละขั้น เปรียบได้กับ
  "สูตรอาหาร" ที่ทำซ้ำได้ผลเหมือนเดิมทุกครั้ง

### 3.3 กลไกชั้นข้อมูล (Layers) — หัวใจที่ทำให้ Docker เร็ว

อิมเมจไม่ได้เป็นก้อนเดียว แต่ประกอบด้วย **ชั้น (layer)** หลายชั้นซ้อนกัน แต่ละคำสั่งใน
Dockerfile สร้างขึ้นหนึ่งชั้น ชั้นเหล่านี้ถูกใช้ซ้ำและแคชไว้ ทำให้เกิดผลสำคัญสองข้อ:

- **ประหยัดพื้นที่ —** อิมเมจหลายตัวที่ใช้ฐานเดียวกัน (เช่น ubuntu:24.04)
  จะใช้ชั้นฐานร่วมกัน ไม่เก็บซ้ำ

- **สร้างซ้ำได้เร็ว —** เมื่อแก้โค้ดแล้วสร้างใหม่ Docker
  จะใช้ชั้นเดิมจากแคชและสร้างใหม่เฉพาะชั้นที่เปลี่ยนแปลงและชั้นที่อยู่ถัดลงไปเท่านั้น

**ผลที่ตามมาซึ่งต้องสอนตั้งแต่ต้น:** ลำดับคำสั่งใน Dockerfile มีผลต่อความเร็วอย่างมาก
ให้วางสิ่งที่เปลี่ยนแปลงน้อย (เช่น การติดตั้งไลบรารี) ไว้ก่อน และสิ่งที่เปลี่ยนบ่อย (เช่น
ซอร์สโค้ด) ไว้ทีหลัง

### 4.1 Docker Engine กับ Docker Desktop ไม่ใช่สิ่งเดียวกัน

| **ส่วนประกอบ**  | **รายละเอียด**                                                                                                                                                               |
|----------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Docker Engine  | แกนหลักที่รันและจัดการคอนเทนเนอร์ ทำงานบน Linux เผยแพร่ภายใต้สัญญาอนุญาต Apache-2.0 (โอเพนซอร์ส) เวอร์ชันเสถียรล่าสุดอยู่ในสาย 29.x (29.7.1 เมื่อ 31 ก.ค. 2026)                                 |

## ส่วนที่ 6: การสร้างอิมเมจด้วย Dockerfile

### 6.1 คำสั่งหลักใน Dockerfile

| **คำสั่ง**   | **หน้าที่**                                                                |
|------------|-------------------------------------------------------------------------|
| FROM       | กำหนดอิมเมจฐานที่จะต่อยอด ต้องเป็นคำสั่งแรกเสมอ                                 |
| WORKDIR    | กำหนดไดเรกทอรีทำงานภายในอิมเมจ (สร้างให้อัตโนมัติหากยังไม่มี)                     |
| COPY       | คัดลอกไฟล์จากเครื่องเราเข้าไปในอิมเมจ                                         |
| RUN        | สั่งรันคำสั่ง "ขณะสร้างอิมเมจ" เช่น ติดตั้งไลบรารี ผลลัพธ์จะถูกบันทึกเป็นชั้นใหม่            |
| ENV        | กำหนดตัวแปรสภาพแวดล้อม                                                    |
| EXPOSE     | ประกาศพอร์ตที่แอปพลิเคชันใช้ (เป็นเอกสารกำกับ ไม่ได้เปิดพอร์ตจริง ต้องใช้ -p ตอนรัน)    |
| CMD        | คำสั่งเริ่มทำงาน "ขณะรันคอนเทนเนอร์" มีได้หนึ่งคำสั่งต่อหนึ่งอิมเมจ และผู้ใช้เขียนทับได้ตอนรัน |
| ENTRYPOINT | คล้าย CMD แต่ผู้ใช้เขียนทับได้ยากกว่า เหมาะกับคอนเทนเนอร์ที่ทำหน้าที่เฉพาะอย่าง          |

| **จุดที่นักศึกษาสับสนบ่อยที่สุด:** RUN ทำงาน "ตอนสร้างอิมเมจ" ส่วน CMD ทำงาน "ตอนรันคอนเทนเนอร์" — การเข้าใจผิดข้อนี้ทำให้เขียน Dockerfile ที่ติดตั้งไลบรารีใหม่ทุกครั้งที่รัน หรือเขียนคำสั่งเริ่มเซิร์ฟเวอร์ไว้ใน RUN แล้วคอนเทนเนอร์ดับทันทีเมื่อรัน |
|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

### 6.4 แนวปฏิบัติที่ดีในการเขียน Dockerfile

- **ระบุเวอร์ชันอิมเมจฐานเสมอ —** ใช้ python:3.12-slim แทน python:latest
  เพื่อให้ผลลัพธ์ทำซ้ำได้

- **เรียงคำสั่งตามความถี่ของการเปลี่ยนแปลง —** สิ่งที่เปลี่ยนน้อยไว้บน สิ่งที่เปลี่ยนบ่อยไว้ล่าง
  เพื่อให้แคชทำงานได้เต็มที่

- **รวมคำสั่ง RUN ที่เกี่ยวข้องเข้าด้วยกัน —** แต่ละ RUN สร้างหนึ่งชั้น การใช้ &&
  เชื่อมคำสั่งติดตั้งและล้างแคชในบรรทัดเดียวช่วยลดขนาดอิมเมจ

- **ไม่รันด้วยสิทธิ์ root —** สร้างผู้ใช้ทั่วไปแล้วใช้คำสั่ง USER
  เพราะโดยค่าเริ่มต้นคอนเทนเนอร์รันด้วยสิทธิ์ root ซึ่งเสี่ยงหากถูกเจาะ

- **ไม่ฝังความลับไว้ในอิมเมจ —** รหัสผ่านและกุญแจ API
  ต้องส่งผ่านตัวแปรสภาพแวดล้อมหรือกลไก secrets ตอนรัน ไม่ใช่เขียนใน Dockerfile
  เพราะทุกคนที่ได้อิมเมจไปจะอ่านได้

- **เลือกอิมเมจฐานให้เล็ก —** รุ่น alpine หรือ slim มีขนาดเล็กกว่ามาก
  ทำให้ดาวน์โหลดเร็วและมีช่องโหว่น้อยกว่า

## ส่วนที่ 7: การจัดเก็บข้อมูลและเครือข่าย

### 7.1 ข้อมูลในคอนเทนเนอร์หายเมื่อลบคอนเทนเนอร์

คอนเทนเนอร์ถูกออกแบบให้ **ไม่ถาวร (ephemeral)**
ข้อมูลที่เขียนลงในคอนเทนเนอร์จะหายไปเมื่อคอนเทนเนอร์ถูกลบ
ซึ่งเป็นบทเรียนที่นักศึกษามักเรียนรู้ด้วยความเจ็บปวดจากการลบฐานข้อมูลของตนเอง
วิธีเก็บข้อมูลถาวรมีสองแบบหลัก:

| **รูปแบบ**  | **ลักษณะ**                                        | **เหมาะกับงาน**                                |
|------------|--------------------------------------------------|-----------------------------------------------|
| Volume     | Docker บริหารจัดการพื้นที่ให้เอง อยู่นอกวงจรชีวิตคอนเทนเนอร์ | ข้อมูลฐานข้อมูล ไฟล์ที่ผู้ใช้อัปโหลด — แนะนำสำหรับงานจริง  |
| Bind mount | ผูกโฟลเดอร์บนเครื่องเราเข้ากับเส้นทางในคอนเทนเนอร์โดยตรง | การพัฒนา — แก้โค้ดบนเครื่องแล้วเห็นผลในคอนเทนเนอร์ทันที |

## ส่วนที่ 8: การจัดการหลายบริการด้วย Docker Compose

### 8.1 เหตุผลที่ต้องใช้ Compose

### 10.1 หลักคิด: AI ช่วยได้ดีกับไวยากรณ์ แต่ไม่รู้จักระบบของเรา

## ส่วนที่ 11: ความปลอดภัยและจริยธรรม

### 11.1 ประเด็นความปลอดภัยที่ต้องสอนตั้งแต่ต้น

- **ไม่ฝังความลับในอิมเมจ —** รหัสผ่านหรือกุญแจ API ที่เขียนใน Dockerfile
  จะติดอยู่ในชั้นข้อมูลของอิมเมจถาวร แม้จะลบในคำสั่งถัดไปก็ยังกู้คืนได้

- **ตรวจสอบที่มาของอิมเมจ —** อิมเมจจาก Docker Hub
  ที่ไม่ทราบที่มาอาจมีมัลแวร์หรือช่องโหว่ ให้เลือกอิมเมจทางการ (Official Images)
  หรืออิมเมจจากผู้เผยแพร่ที่ยืนยันตัวตนแล้ว

- **อัปเดตอิมเมจฐานสม่ำเสมอ —** อิมเมจที่สร้างไว้นานย่อมมีช่องโหว่ที่ค้นพบภายหลัง
  ควรสร้างใหม่และสแกนหาช่องโหว่เป็นระยะ

- **จำกัดสิทธิ์ให้น้อยที่สุด —** ไม่รันด้วย root ไม่ใช้ตัวเลือก --privileged โดยไม่จำเป็น
  และไม่ผูกซ็อกเก็ตของ Docker เข้าไปในคอนเทนเนอร์ที่ไม่ไว้ใจ

- **ระวังการเปิดพอร์ต —**
  การแม็ปพอร์ตบนเครื่องที่มีไอพีสาธารณะเท่ากับเปิดบริการนั้นสู่อินเทอร์เน็ต
  ต้องตรวจสอบไฟร์วอลล์และการตั้งรหัสผ่านเสมอ

### 11.2 ความซื่อสัตย์ทางวิชาการ

- **เปิดเผยการใช้ AI (AI Log) —** ระบุเครื่องมือ prompt ที่ใช้ และส่วนที่ AI มีส่วนช่วย
  แนบท้ายรายงานทุกครั้ง

- **ต้องอธิบายทุกบรรทัดในไฟล์ที่ส่งได้ —** ผู้สอนจะสุ่มถามความหมายของคำสั่งในการสอบปฏิบัติ
  การคัดลอกไฟล์มาโดยไม่เข้าใจถือว่าไม่ผ่าน

- **อ้างอิงแหล่งที่มาของอิมเมจและโค้ด —** อิมเมจและตัวอย่างโค้ดมีสัญญาอนุญาตกำกับ
  ต้องระบุที่มาและปฏิบัติตามเงื่อนไข

  แล้วเปิดหน้าเว็บให้ได้ จากนั้นเปลี่ยนหมายเลขพอร์ตและตั้งชื่อคอนเทนเนอร์ให้ต่างกัน
  สังเกตว่าเกิดอะไรขึ้นเมื่อสองคอนเทนเนอร์ใช้พอร์ตเดียวกัน —
  เรียนรู้แนวคิดการแม็ปพอร์ตจากข้อผิดพลาดจริง

- **กิจกรรม 2 — แข่งลดขนาดอิมเมจ (35 นาที):** แจก Dockerfile ที่เขียนไม่ดี
  (ใช้อิมเมจฐานเต็มรูปแบบ เรียงคำสั่งผิด รันด้วย root)
  ให้แข่งกันปรับปรุงให้อิมเมจเล็กที่สุดโดยที่โปรแกรมยังทำงานได้ วัดผลด้วยคำสั่ง docker
  images แล้วอภิปรายเทคนิคที่แต่ละกลุ่มใช้

- **กิจกรรม 3 — ล่าบั๊ก Compose (30 นาที):** ผู้สอนแจกโปรเจกต์ที่มีข้อผิดพลาดฝังไว้ 4
  จุด (เช่น ใช้ localhost แทนชื่อบริการ, ลืมประกาศ volume, ระบุพอร์ตสลับด้าน, ใช้ฟิลด์
  version ที่เลิกใช้) ให้แข่งกันหาและแก้พร้อมบันทึกวิธีวินิจฉัย

- **กิจกรรม 4 — AI Review Lab (40 นาที):** ใช้ Prompt 2 และ 3 ในส่วนที่ 10 กับ
  Dockerfile ของตนเอง แล้วบันทึกลงตารางว่า AI ชี้จุดใดถูกต้อง จุดใดผิดหรือล้าสมัย
  และจุดใดที่ AI มองไม่เห็นแต่มนุษย์เห็น — ปิดท้ายด้วยการอภิปรายว่าเหตุใด AI
  จึงมักแนะนำไวยากรณ์เก่าในหัวข้อนี้

- **กิจกรรม 5 — ส่งต่อโปรเจกต์ (25 นาที):**
  แต่ละกลุ่มส่งโฟลเดอร์โปรเจกต์ให้กลุ่มอื่นทดลองรันบนเครื่องของตน
  กลุ่มที่รับต้องรันให้สำเร็จด้วยคำสั่งเดียวโดยไม่ถามเจ้าของ — บททดสอบที่แท้จริงว่าโปรเจกต์
  "ทำซ้ำได้" จริงหรือไม่

## ส่วนที่ 13: แบบฝึกหัด/คำถามท้ายบท (พร้อมแนวคำตอบ)

### 13.1 คำถามทบทวน

1.  **อธิบายความแตกต่างระหว่างอิมเมจกับคอนเทนเนอร์** แนวตอบ:
    อิมเมจคือแม่แบบแบบอ่านอย่างเดียวที่บรรจุระบบไฟล์และคำสั่งเริ่มทำงาน
    ส่วนคอนเทนเนอร์คืออิมเมจที่ถูกนำมารันเป็นกระบวนการจริง
    หนึ่งอิมเมจสร้างได้หลายคอนเทนเนอร์

2.  **เหตุใดคอนเทนเนอร์จึงเบาและเริ่มทำงานเร็วกว่าเครื่องเสมือน** แนวตอบ:
    เพราะใช้เคอร์เนลของระบบปฏิบัติการโฮสต์ร่วมกัน
    ไม่ต้องบูตระบบปฏิบัติการของตนเองและไม่ต้องจำลองฮาร์ดแวร์

3.  **คำสั่ง RUN กับ CMD ใน Dockerfile ต่างกันอย่างไร** แนวตอบ: RUN
    ทำงานขณะสร้างอิมเมจและผลลัพธ์ถูกบันทึกเป็นชั้นข้อมูล ส่วน CMD
    คือคำสั่งเริ่มทำงานเมื่อรันคอนเทนเนอร์ และมีผลได้เพียงคำสั่งเดียวต่ออิมเมจ

4.  **เพราะเหตุใดจึงควรคัดลอกไฟล์ requirements.txt ก่อนคัดลอกซอร์สโค้ดทั้งหมด**
    แนวตอบ: เพื่อให้กลไกแคชของชั้นข้อมูลทำงาน — ตราบใดที่รายการไลบรารีไม่เปลี่ยน
    ขั้นตอนติดตั้งไลบรารีจะถูกใช้จากแคช ทำให้การสร้างอิมเมจซ้ำเร็วขึ้นมาก

5.  **Volume ต่างจาก Bind mount อย่างไร และควรใช้แบบใดกับฐานข้อมูล** แนวตอบ:
    Volume ให้ Docker บริหารพื้นที่เอง เหมาะกับข้อมูลถาวรเช่นฐานข้อมูล ส่วน Bind
    mount ผูกโฟลเดอร์บนเครื่องเราโดยตรง เหมาะกับการพัฒนาที่ต้องแก้โค้ดแล้วเห็นผลทันที —
    ฐานข้อมูลควรใช้ Volume

6.  **เหตุใดคอนเทนเนอร์จึงเรียกหากันด้วย localhost ไม่ได้** แนวตอบ: localhost
    ภายในคอนเทนเนอร์หมายถึงตัวคอนเทนเนอร์นั้นเอง ต้องใช้ชื่อบริการหรือชื่อคอนเทนเนอร์ซึ่ง
    Docker แปลงเป็นเลขที่อยู่ไอพีให้ผ่านบริการ DNS ภายในเครือข่ายเดียวกัน

7.  **คำสั่ง docker-compose (มีขีดกลาง) กับ docker compose (เว้นวรรค)
    ต่างกันอย่างไรในปัจจุบัน** แนวตอบ: แบบมีขีดกลางคือ Compose รุ่นที่ 1
    ซึ่งหมดการสนับสนุนแล้ว ปัจจุบันต้องใช้แบบเว้นวรรคซึ่งเป็นส่วนขยายของ Docker CLI
    และควรลบฟิลด์ version: ออกจากไฟล์ Compose ด้วย

8.  **(วิเคราะห์)** นักศึกษารัน docker compose up -d
    แล้วบริการเว็บดับทันทีโดยฐานข้อมูลยังทำงานอยู่ จงเสนอลำดับขั้นการวินิจฉัย 4 ขั้น
    แนวตอบ: (1) docker compose ps ดูรหัสสถานะการออก (2) docker compose
    logs web อ่านข้อความสุดท้ายก่อนดับ (3)
    ตรวจสอบตัวแปรสภาพแวดล้อมและสายเชื่อมต่อฐานข้อมูลว่าใช้ชื่อบริการถูกต้องหรือไม่ (4)
    ตรวจว่ามี healthcheck และ condition: service_healthy หรือไม่
    เพราะอาจเชื่อมต่อก่อนฐานข้อมูลพร้อม

### 13.2 แบบฝึกหัดปฏิบัติ (ส่งเป็นชิ้นงาน)

- **แบบฝึกหัด A — บรรจุแอปพลิเคชันของตนเอง:** นำโปรเจกต์ที่เคยพัฒนาในรายวิชาอื่น
  (เว็บแอปพลิเคชันหรือ API) มาเขียน Dockerfile, .dockerignore และ
  compose.yaml ที่มีอย่างน้อย 2 บริการ (แอปพลิเคชัน + ฐานข้อมูล) พร้อม volume
  สำหรับข้อมูลถาวรและ healthcheck ส่งเป็นรีโพซิทอรี Git พร้อม README
  ที่อธิบายวิธีรันด้วยคำสั่งเดียว และแนบภาพผลการรัน

- **แบบฝึกหัด B — รายงานการปรับปรุงและการใช้ AI:**
  บันทึกตารางเปรียบเทียบขนาดอิมเมจก่อนและหลังการปรับปรุงพร้อมอธิบายว่าทำอะไรไป
  และบันทึกการแก้ปัญหาอย่างน้อย 3 ครั้งในรูปแบบ: อาการ / สมมติฐานของตนเอง / prompt
  ที่ใช้ / คำตอบของ AI / ผลตรวจสอบจริง (ถูกหรือผิด) / วิธีแก้สุดท้าย
  ปิดท้ายด้วยข้อสรุปครึ่งหน้าว่า AI ให้คำตอบล้าสมัยในเรื่องใดบ้าง
